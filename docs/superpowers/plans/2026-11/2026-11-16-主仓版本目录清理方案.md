# 主仓版本目录只保留当前版本方案

状态：2026-11-16 用户确认按 A 方案实施；提交前审查、插件全量回归及离线真实升级冒烟已完成，发布版本号与最终文案另行确认。

## 结论

当前实现并非完全不清理：`bootstrap.prune_runtimes()` 会删除 `.releases/release-*` 中由自举器创建、且不属于活动或回滚版本的目录。但它固定保护“活动版本 + 上一版本”两份，且在健康确认后仍保留上一版本。因此稳定状态下至少有 **2 份完整主仓运行时**，每份都带独立 `venv`。

更关键的是，首次安装使用的根目录布局 `instance/src`、`instance/venv` 不在 `.releases` 扫描范围内。升级到 `.releases` 后，根目录副本不会再被任何清理逻辑处理，会永久残留。实际磁盘上常见组合是：

| 目录 | 是否会被现有逻辑删除 |
| --- | --- |
| `instance/.releases/release-当前` | 保留（活动版本） |
| `instance/.releases/release-上一版` | 保留（回滚版本） |
| `instance/src`、`instance/venv` | 永久保留（旧根目录布局） |
| 升级失败留下的 `release-*` | 下一次清理时删除，失败期间暂时保留 |
| 无 `.bootstrap-runtime.json` 或标记不匹配的目录 | 永久保留（防止误删用户目录） |

本机主仓开发环境 `venv` 约 1.6 GiB、6.6 万个文件，仅作量级参考；生产实例的依赖集不同，但每份运行时通常也是数百 MiB 到 1 GiB 级别。三份叠加就足以造成明显磁盘压力。

2026-11-16 对运行中实例做只读检查，确认实际就是三份布局：

| 目录 | 版本 | 大小 |
| --- | --- | --- |
| `.releases/release-fs1q0bb9`（活动） | Stock Robot v0.3.2 | 869 MiB |
| `.releases/release-4lowi3dg`（上一版） | Stock Robot v0.3.1 | 869 MiB |
| 根目录 `src` + `venv` | Stock Robot v0.2.1 | 12 MiB + 851 MiB |

合计约 2.6 GiB；服务器根盘 40 GiB 已用 85%。活动版本包含 27,150 个文件，旧根目录 `venv` 包含 26,096 个文件，删除必须放到线程中执行。

## 目标与非目标

目标：

- 只保留当前活动、健康、且与插件 `MANAGED_RELEASE_TAG` 匹配的运行时。
- 删除其余由自举器拥有（有明确 owner 标记）的 `release-*` 目录。
- 活动版本迁入 `.releases` 并确认健康后，删除旧根目录 `instance/src`、`instance/venv`、`instance/install-state.json`。
- 不触碰配置、报告、缓存、未知目录和用户手工放入的文件。

非目标：

- 不清理 `uv` / `pip` 的全局缓存；这些缓存可能被其他项目共享，应由用户手动执行 `uv cache prune` 或 `pip cache purge`。
- 不删除 `instance/.stock_robot/`、`instance/reports/`、`delivery_tmp/` 等数据目录。
- 不处理外部启动、非本插件管理的服务实例。

## 方案对比

| 方案 | 行为 | 磁盘占用 | 风险/成本 |
| --- | --- | --- | --- |
| A. 健康检查通过后立即删上一版 | 候选启动并 `/health` 成功后，清除 `previous` 指针并删除旧版本 | 稳定 1 份 | 失去本地回滚；新版本若在运行期才出问题，需要重新安装 |
| B. 保留上一版（当前） | `previous` 永久保护，直到下一次成功升级 | 稳定 2 份 | 回滚能力最好，但不满足“只留当前” |
| C. 增加 `keep_previous_runtime` 配置 | 默认只留当前，用户可开启保留上一版 | 默认 1 份 | 多一个配置项和同步/迁移逻辑，当前配置页已精简为六项 |
| D. 共享 venv / 硬链接 / 依赖去重 | 多个版本共用一套依赖 | 最低 | 实现复杂，跨平台和升级原子性风险高，不适合插件自举场景 |

推荐 **A**，并补上旧根目录清理和失败候选清理。C 可以作为后续可选项，不建议首轮引入。

## 推荐实现

### 1. `bootstrap.py`：清理策略改为“只保护活动版本”

- 增加统一 owner 常量和判断函数，避免多次解析 `.bootstrap-runtime.json`。
- `prune_runtimes(instance, *, keep_previous=False)`：
  - 默认 `protected = {runtime_path(instance)}`，只保护活动版本。
  - `keep_previous=True` 时再保护指针中的 `previous`，仅用于升级尚未确认健康的窗口。
  - 只处理 `.releases` 下以 `release-` 开头、是目录、通过 `safe_path()`、且 owner 标记完全匹配的候选。
  - 删除失败只记录警告，下一次启动继续重试，不影响服务。
- `confirm_runtime(instance, *, drop_previous=False)`：
  - 清除 `pending_health`。
  - `drop_previous=True` 时从指针中移除 `previous`，避免指针指向即将删除的目录。
- `rollback_runtime()`：
  - `previous` 缺失、不是合法相对路径、目录不存在时返回 `False`，不切换到已删除目录。
- 新增 `prune_legacy_runtime(instance)`：
  - 仅当 `runtime_path(instance) != instance`（活动版本已在 `.releases`）时执行。
  - 校验根目录 `install-state.json` 和 `src/.bootstrap-source.json`，确认是自举器安装的旧布局后再删除 `src`、`venv`、`install-state.json`。
  - 不删除根目录的 `.stock_robot`、`reports` 等数据。
- `upgrade_instance()`：
  - 清理时使用 `keep_previous=runtime_pending(instance)`，升级窗口内保留回滚目标。
  - 若指针仍处于 `pending_health`（上次切换后未确认健康），新的候选应继承原 `previous`（最后已知可用的版本），而不是把未确认的候选当作回滚目标；否则候选损坏时可能回滚到另一个坏版本。
  - 升级失败留下的候选目录由下一次清理处理；也可以在失败路径立即删除，但要注意 Windows 文件锁和取消场景。
  - 清理是同步文件操作，包含数万文件，异步调用方应使用 `asyncio.to_thread()`，避免阻塞事件循环。

### 2. `launcher.py`：健康确认后真正删除

- `_prepare()` 成功启动后：
  - `confirm_runtime(self.instance, drop_previous=True)`
  - `await asyncio.to_thread(prune_runtimes, self.instance)`
  - `await asyncio.to_thread(prune_legacy_runtime, self.instance)`
- 启动时如果直接复用健康服务，可在拿到 `managed-service.lock` 的前提下做一次 `.releases` 清理；拿不到锁说明另一个实例正在准备/升级，跳过，避免删掉别人的候选目录。
- 旧根目录清理只在“本次由插件启动了 `.releases` 版本且健康”后执行，不在仅复用外部服务时执行，避免误删用户手工启动的根目录服务。

### 3. 删除安全

- 只删除有 `{"owner": "stock-robot-bootstrap-v1"}` 标记的目录；未知目录永久保留并记录一次提示。
- 删除前重新校验 `safe_path()`，拒绝符号链接、Windows 重解析点和越界路径。
- 活动版本永远不进入删除列表；即使指针异常，也只是跳过清理，不做猜测性删除。
- Windows 只读文件、被杀毒软件/旧进程短暂占用时，清除只读位并有限重试；仍失败则记录警告，下一次启动再试。
- 删除放到线程中执行，避免 6 万级文件删除阻塞 AstrBot 事件循环。
- 清理失败不影响服务启动；日志中记录目录名和错误类型，不记录凭据。

### 4. 测试

- `prune_runtimes()` 默认删除上一版，只保留活动版本。
- `keep_previous=True` 时保留回滚目标。
- `confirm_runtime(drop_previous=True)` 后指针不再引用上一版，`rollback_runtime()` 返回 `False`。
- 活动版本、未知目录、owner 标记不匹配的目录永远不会被删除。
- 旧根目录在活动版本确认后删除；活动版本仍在根目录时绝不删除。
- 升级失败候选目录在下一次清理或下一次成功启动时删除。
- Windows 只读文件、删除失败、并发锁跳过等边界。
- 更新 `tests/test_managed_upgrade_smoke.py` 中“回滚后仍检查候选目录”的断言。

### 5. 文档

- 更新 `docs/维护与排障.md`：说明健康确认后只保留当前版本、旧根目录会被回收、升级窗口内仍有回滚副本。
- 更新 `CHANGELOG.md` 和版本号，明确这是一次磁盘占用行为变化。
- 在 README/维护文档中补充手动诊断命令，便于用户确认 `.releases` 和旧根目录的实际大小。

## 风险与取舍

- **失去本地回滚**：健康检查通过是最后一道自动门。若新版本启动健康但运行期出错，插件只能按绑定的 `MANAGED_RELEASE_TAG` 重新安装，不能一键回退到上一版。这是“只留当前”的必然代价。
- **旧根目录可能是手工服务**：自动删除前要求活动版本已在 `.releases` 且由本次插件启动成功；仅复用外部服务时不删。
- **Windows 文件锁**：旧服务进程、杀毒软件可能短暂占用 `venv` 文件；删除失败会在下一次启动重试，不应视为致命错误。
- **大目录删除耗时**：单份 `venv` 可能有数万文件，必须异步执行，并接受清理在后台完成。
- **并发实例**：清理必须与 `managed-service.lock` 协调；拿不到锁时跳过，宁可少删不可误删。

## 建议的验收标准

1. 升级前存在“根目录旧版 + `.releases` 活动版 + `.releases` 上一版”，成功启动后只剩活动版，根目录 `src`/`venv` 被删除。
2. 升级候选启动失败时，回滚到上一版仍成功；回滚成功后失败候选目录被清理。
3. 未知目录、无 owner 标记目录、`reports`、`.stock_robot`、`delivery_tmp` 全部保留。
4. Windows 与 Linux 隔离目录实测；记录清理前后 `du`/目录大小和耗时。
5. 全量 pytest、Ruff、格式检查通过。
