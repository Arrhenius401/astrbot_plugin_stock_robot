依据：旧分支 `codex/report-native-t2i-wip` 中的 `docs/superpowers/plans/2026-10/2026-10-10-报告独立渲染与清理设计.md`。本文独立保存二阶段方案，旧文档中的独立排版、浏览器和双字重字体方案不再作为实现依据。

## 当前实现与变化

- `ReportRenderer` 调用 AstrBot 原生字生图，读取为内存 PNG 后删除本次框架输出。
- `ReportDelivery` 图片成功时不保存副本；Markdown/ZIP 兜底使用临时目录，发送结束后回收。二阶段需要新增最终产物留存。
- `main.py` 在分析开始前预留名额，交付结束才释放；这段完整生命周期应纳入清理保护。
- 安装进度、安装命令和自有服务输出分别追加到 `service.log`，需统一写入和轮转，避免 Windows 打开文件时重命名失败及多写入入口竞争。
- 已检查的 Stock Robot v0.1.0 默认写入工作目录下 `reports/stock|index/<代码>/<YYYY-MM>/<代码>_<时间>.md`。插件启动服务的工作目录是 `instance`，不能误用 `instance/src/reports`，也不能假定后续版本布局相同。
- 当前 launcher 在健康探测成功时可以直接复用服务；本地安装记录不证明该端点当前由插件持有。

## 沿用的规则

| 对象 | 期限/预算 | 行为 |
| --- | --- | --- |
| 成功交付的最终 PNG 与完整 Markdown | 24 小时 | 从任务结束时计算；图片成功也保存 Markdown |
| 渲染或发送失败的完整报告与有效图片 | 72 小时 | 图片失败但文件成功仍按失败产物；没有有效图片不伪造 PNG |
| 简要诊断 | 7 天 | 不保存报告正文、模型凭据或原始异常全文 |
| 已结束任务的产物 | 256 MiB | 到期优先，仍超限按结束时间淘汰最旧任务产物 |
| 清理触发 | 初始化、每 10 分钟、新任务开始前 | 文件扫描与删除放入后台线程，并统一互斥 |

产物位于插件数据目录 `delivery_tmp/<随机任务ID>/`，任务元数据记录所有权、文件、阶段、结束时间与保留类别；诊断独立保存，产物淘汰后仍可追溯清理原因。中间文件立即回收，ZIP 只作传输中间文件，保留其完整 Markdown 原文。

活动任务、正在运行的文件工作线程及上传中的文件不参与淘汰。256 MiB 只约束已结束任务的保留产物，不覆盖活动任务、服务原始报告、依赖、字体或整个主机。期限是最长保留期，容量压力可提前淘汰。留存失败不得把已成功的发送改判为失败；记录原因并继续服务。报告副本是本地完整内容，属于用户可复制的排查资料，应在 README 说明保留行为。

## 原始报告清理

唯一新增用户配置 `cleanup_previous_reports`，布尔值，默认 `false`；修改后重载生效。

开启后，仅处理经过归属和版本布局验证的插件自建服务，按文件修改时间删除超过 7 天的已识别股票/指数 Markdown。没有独立容量淘汰规则，不纳入 256 MiB。未知文件、附属文件和未知布局保持原样，记录跳过原因；只移除清理后为空且已验证的报告子目录。报告库直接枚举文件，无需维护独立索引。

不处理配置、数据库、会话、回测、雷达、缓存、依赖、字体、用户保存副本、AstrBot 全局缓存或协议端群文件。外部地址和共享/仅健康复用的服务不执行删除。

新增建议：要求当前插件确实持有服务进程，再结合安装/来源记录与实际报告写入布局验证服务归属。插件存在分析、下载、交付或安装任务时跳过原始报告删除，清理期间阻止新的插件分析进入。版本兼容通过明确验证记录决定，不能只看到类似目录就视为兼容。

限制：插件互斥只能覆盖插件请求，不能保护 Web、定时订阅或其他客户端正在进行的工作；本轮不修改分析服务 API、不承诺共享服务并发清理安全。HTTP 请求超时/取消也不证明服务端任务已停止；若存在未确认结束的请求，跳过原始报告清理，直到能够确认安全。不能靠固定等待时间猜测服务端结束。

## 本次补充并已确认的规则

- 诊断记录预算 16 MiB：到期优先，仍超限删除最旧记录。
- `service.log` 每份 10 MiB，最多 5 份（含当前文件，合计约 50 MiB）；归档最多 7 天，当前写入文件不按年龄删除。安装和运行输出共用轮转写入入口，持续排空子进程管道，写盘失败不使子进程堵塞。
- 取消或异常退出后，已取得的完整报告和有效图片按失败产物保留 72 小时；没有最终报告的中间文件回收，独立保留简要诊断。
- 旧版遗留目录没有可信任务元数据时，不猜测归属或时间并删除；记录提示。二阶段运行创建的目录以版本化元数据识别，异常退出后由下一次初始化恢复处理。
- 已有超大 `service.log` 在首次写入前纳入轮转预算；这会删除较旧内容，不承诺完整保留历史。迁移以分块方式保存符合预算的尾部，避免整份日志读入内存；不触碰分析服务自身的其他日志。

## 删除安全与失败处理

校验固定根目录及每层祖先，不跟随符号链接或 Windows 重解析点；验证最终解析路径仍在所有权根目录内。不能递归删除未经验证的计算路径。扫描后删除前重新检查活动状态、类型及归属；删除失败记录诊断后继续，不阻止分析。多进程/多实例无法取得独占清理权时跳过删除，不能仅凭同一进程的任务集合判定其他进程已结束。

同一清理模块管理留存、周期检查和诊断；`report_delivery.py` 接入任务状态与最终产物；`main.py` 管理初始化、分析保护及停用回收；`launcher.py`/`bootstrap.py` 接入服务归属和统一日志写入；配置与 README 描述开关及固定规则。新增功能放在独立分支，不改变版本号，不自动提交、合并、推送或部署。

## 成本与验收

不新增第三方包、浏览器、系统服务或在线清理接口，使用现有 Python 标准库能力。相较当前立即回收模式，会主动增加排查副本占用：已结束产物 256 MiB、诊断 16 MiB、插件服务日志约 50 MiB，合计约 322 MiB；这是不同预算的合计，不是整个插件磁盘硬上限。扫描、临时文件和活动报告还有额外占用，内存峰值尚未实测，需记录真实验收结果。报告本身的原生渲染成本保持现有行为。

隔离测试覆盖期限边界、容量顺序、成功/失败/取消留存、异常退出恢复、旧目录保留、文件线程/上传保护、磁盘和权限失败、符号链接/重解析点、跨进程竞争、开关默认关闭、共享服务和未知版本跳过、报告布局与空目录清理、现有大日志迁移、运行中轮转及脱敏。Windows 和 Linux 使用隔离目录做真实文件/进程验收，不删除生产历史报告；macOS 无环境则明确未实测。最后执行仓库回归并记录磁盘及进程内存变化，不因测试通过推断共享服务并发安全。
